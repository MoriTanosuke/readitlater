# Leseliste (Read-it-later-App)

Artikel per URL speichern, Volltext durchsuchen, mit Schlagwörtern versehen und als gelesen markieren. Mehrere Benutzer, jeder sieht nur seine eigenen Daten.

## Stack

- **Backend** (`/backend`): Rust, axum, tokio, sqlx (SQLite, eingebettete Migrationen), argon2, eigene Session-Verwaltung
- **Frontend** (`/frontend/public`): nur HTML, CSS und JavaScript (ES-Module). Der Code bleibt statisch: keine npm-Pakete, keine Buildchain, kein Transpiler oder Bundler. Npm ist nur für Testwerkzeuge in `/frontend/tests` erlaubt (siehe Entscheidung „Tests“), sie gehören nie in die Images.
- **Auslieferung**: Das Backend liefert das Frontend selbst aus dem Binary (`static_files.rs`, rust-embed), `/api/*` ist die Schnittstelle. Dadurch gibt es nur eine Origin und kein CORS. HTTPS und Zertifikate übernimmt der vorhandene Caddy des Betreibers als Reverse-Proxy (nur `reverse_proxy`).
- **Deployment**: GitHub Actions baut ein Image nach ghcr.io (`<repo>`, Dockerfile im Repository-Wurzelverzeichnis), Watchtower (Fork `nicholas-fedor/watchtower`) zieht sie auf dem Server. Der Push auf `main` deployt automatisch.
- **Daten**: SQLite im WAL-Modus, Datei liegt im Volume `/data`, nie im Image.

## Befehle

```sh
cd backend
cargo fmt && cargo clippy --all-targets -- -D warnings && cargo test   # vor jedem Push
DATABASE_PATH=./data/app.db cargo run                                   # Backend lokal auf :3000

# Frontend-Tests (echtes Frontend in jsdom gegen das gebaute Backend; Node 22)
cd backend && cargo build && cd ../frontend/tests && npm ci && npm test

# Frontend ändern: im Debug-Build liest das Backend frontend/public von der Platte, Neuladen genügt.
# Einbettung auch im Debug-Build prüfen: cargo run --features rust-embed/debug-embed
```

Konfiguration nur über Umgebungsvariablen: `DATABASE_PATH`, `BIND_ADDR`, `REGISTRATION_ENABLED`, `COOKIE_SECURE`, `SESSION_DAYS`, `RUST_LOG`, `FETCH_ALLOW_PRIVATE` (Standard false, schaltet den SSRF-Schutz ab, nur für Tests/vertrauenswürdige Netze), `FETCH_TIMEOUT_SECS` (15), `FETCH_MAX_BYTES` (2 MiB), `FETCH_CONCURRENCY` (4), `IMAGE_STORE_ENABLED` (Standard true), `IMAGE_CONCURRENCY` (2), `IMAGE_MAX_BYTES` (10 MiB), `RATE_LIMIT_ENABLED` (Standard true), `PASSKEY_ORIGIN` (z. B. `https://lesen.kopis.de`; ohne Angabe sind Passkeys aus), `PASSKEY_RP_ID` (optional, Standard: Host aus `PASSKEY_ORIGIN`).

Betreiber-Befehl (im Image gibt es keine Shell): `docker compose exec app /app/readlater-backend reset-credentials <E-Mail> [--revoke-passkeys] [--revoke-share-tokens] [--password-stdin]`

## Arbeitsweise

- Änderungen immer auf einem Branch mit Pull Request, nie direkt auf `main`.
- Schemaänderungen nur als neue Migration in `backend/migrations`, bestehende Migrationen nie verändern.
- Neue Abhängigkeiten sparsam einführen und kurz begründen.
- Antworten und Code-Kommentare auf Deutsch, Bezeichner auf Englisch.
- Wichtige Entscheidungen hier festhalten.

## Entscheidungen

- **Tests**: Rust-Tests (Unit und Integration) liegen in `backend`. Die Frontend-Tests in `frontend/tests` starten das echte Backend mit frischer temporärer Datenbank und einen lokalen Testserver für die Artikelseiten und laden `index.html` samt `app.js` in jsdom (`node --test`). `FETCH_ALLOW_PRIVATE=true` ist dafür gesetzt. Die CI führt beides im Job `test` aus (Backend mit `cargo nextest run --profile ci`, Frontend mit `npm run test:ci`; beide schreiben JUnit-Berichte, die `dorny/test-reporter` als Check-Runs „Backend-Tests“ und „Frontend-Tests“ anzeigt; `junit-wrap.mjs` packt die Node-Ausgabe in ein `<testsuite>`, das der Reporter braucht; lokal genügen `cargo test` und `npm test`), die Image-Builds laufen erst danach (`needs: test`). Ein anderes Backend-Programm lässt sich mit `BACKEND_BIN` angeben. **Regel (vom Betreiber festgelegt):** Das Vorgehen gilt nur, solange das Frontend statisch bleibt, ohne npm-Pakete und ohne Buildchain für den Frontend-Code. Als Testwerkzeug ist jsdom erlaubt, für Smoketests gegen die laufenden Container auch Playwright. Weitere Testabhängigkeiten nur sparsam und mit kurzer Begründung.

- **Sessions**: zufälliges Token (32 Byte) im Cookie `session` (HttpOnly, SameSite=Lax, optional Secure). In der Datenbank steht nur der SHA-256-Hash.
- **Passwörter**: argon2id (Standardparameter), mindestens 10 Zeichen. Login prüft auch bei unbekannter E-Mail einen Hash und gibt immer dieselbe Fehlermeldung zurück.
- **CSRF**: Alle Anfragen außer GET/HEAD/OPTIONS brauchen den Header `X-Requested-With`. Das Frontend setzt ihn in `js/api.js`.
- **Passwort ändern**: `PUT /api/account/password` mit bisherigem und neuem Passwort (gleiche Regeln wie bei der Registrierung). Danach werden alle Sessions des Benutzers gelöscht und für das aktuelle Gerät wird eine neue angelegt.
- **Suche**: SQLite FTS5 (Migration 0003) als External-Content-Index `articles_fts` über `title` und `content_text`, per Trigger für Insert, Update und Delete aktuell. Tokenizer `unicode61 remove_diacritics 2` (Umlaute werden gefaltet). Der Suchtext wird nie roh an FTS5 gegeben: jedes Wort wird als Phrase in Anführungszeichen gesetzt, das letzte als Präfix, alle müssen vorkommen (`search_query` in `articles.rs`). Sortierung nach Relevanz (bm25), Treffer im Auszug stehen zwischen den Steuerzeichen U+0001 und U+0002 und werden im Frontend per DOM als `<mark>` gesetzt.
- **Schlagwörter und Gelesen-Status**: `PATCH /api/articles/{id}` mit `is_read` und/oder `tags` (Liste ersetzt die bisherigen). Schlagwörter sind pro Benutzer, ohne Beachtung der Groß-/Kleinschreibung eindeutig, max. 40 Zeichen, max. 20 pro Artikel, keine Kommas. Nicht mehr verwendete Schlagwörter werden automatisch gelöscht. `GET /api/tags` liefert Name und Anzahl, `GET /api/articles` filtert mit `q`, `tag` und `read`.
- **Konto-Menü**: Die E-Mail oben rechts öffnet ein Menü (Disclosure-Muster mit `aria-expanded`, schließt bei Escape, Klick daneben und Navigation). Passwort ändern und Konto löschen haben eigene Seiten unter `#/account/password` und `#/account/delete` mit „Abbrechen“ zurück zur Liste. Nach erfolgreicher Passwortänderung zeigt die Liste einmalig einen Hinweis. Die Backend-API ist unverändert.
- **Konto löschen**: erfordert das Passwort. Artikel, Schlagwörter und Sessions verschwinden per `ON DELETE CASCADE` (Fremdschlüssel sind pro Verbindung aktiviert, siehe `db.rs`).
- **Teilen aus anderen Apps**: `POST /api/share` mit `Authorization: Bearer <Token>` (Android HTTP Shortcuts, iOS Kurzbefehle). Tokens (Migration 0004, `share_tokens`) werden in der Weboberfläche unter `#/account/share` angelegt (`/api/share-tokens`, nur per Session, max. 10 pro Benutzer), haben das Präfix `lsl_`, 32 Byte Zufall, in der Datenbank nur der SHA-256-Hash. Ein Token gilt **nur** für `/api/share` (Least Privilege: kann Artikel hinzufügen, nichts lesen oder löschen) und lässt sich einzeln widerrufen. `/api/share` liegt außerhalb des CSRF-Guards, weil es nur den Header `Authorization` auswertet und kein Cookie. Der Body darf JSON, Formular oder reiner Text sein, die erste http(s)-Adresse im Text zählt (Android teilt „Titel Adresse“). Gespeichert wird über `articles::save_article`, es gelten SSRF-Schutz, Duplikatprüfung und Abruf-Limit wie bei `POST /api/articles`. Eine Passwortänderung widerruft Tokens nicht, sie sind eigene Zugangsdaten.
- **Ratenbegrenzung** (`ratelimit.rs`, Crate `governor`, nur Speicher, bewusst nicht in SQLite: jede Anfrage wäre sonst ein Schreibzugriff auf den einzigen Schreiber): Stufen mit Token-Bucket pro Schlüssel. `general` (120 sofort, danach 2/s pro IP, alle Routen außer `/health`, äußerste Middleware), `auth` (10 sofort, danach 1 alle 6 s pro IP, Login, Registrierung, Passwort ändern, Konto löschen), `login_pair` (IP und E-Mail: 5, danach 1/min) und `login_email` (E-Mail allein: 30, danach 1 alle 2 min, bremst verteilte Angriffe), `password_user` (pro Benutzer bei Passwort ändern und Konto löschen: 5, danach 1/min), `fetch_user` (pro Benutzer: 10, danach 1 alle 6 s) in `articles::save_article`, damit Speichern und Teilen dasselbe Kontingent teilen. Duplikate zählen nicht. Antwort 429 mit `Retry-After`. Die Prüfung steht vor Body-Parsing, Anmeldung und Hashing. Weil die IP-Stufen vorher greifen, ist die Zahl der E-Mail-Schlüssel begrenzt. Ein Hintergrundjob entfernt jede Minute erholte Einträge. Client-IP: letzter Eintrag von `X-Forwarded-For` (den hängt der vorgeschaltete Caddy an, vom Client mitgeschickte Werte stehen davor), sonst die Adresse der Verbindung; IPv6 zählt als /64. Das Backend darf deshalb nie direkt aus dem Internet erreichbar sein (nur über den Reverse-Proxy). Grenzen des Ansatzes: Ein Neustart setzt die Zähler zurück; `login_email` kann ein Konto für kurze Zeit für alle bremsen (bewusst, statt harter Sperre). Die Tests schalten die Begrenzung ab (`RATE_LIMIT_ENABLED=false`), außer `tests/ratelimit.rs`.
- **Export und Import** (`transfer.rs`): `GET /api/export` liefert alle Artikel des angemeldeten Benutzers als eine JSON-Datei (`{"format":"leseliste-export","version":1,"exported_at":…,"articles":[…]}`), ohne E-Mail, Ids oder Tokens. Die Antwort wird in Blöcken zu 50 Artikeln gestreamt (konstanter Speicher). Im Frontend ist es ein normaler Link mit `download`, es braucht nur Browser-Bordmittel (keine Kompression, keine Fremdwerkzeuge). `POST /api/import` akzeptiert ausschließlich dieses Format (kein Pocket, Instapaper o. Ä., bewusst). Der Benutzer exportiert und importiert nur seine eigenen Daten: Benutzer und Ids aus der Datei werden ignoriert. Dateiinhalt gilt als feindlich: URL wird wie beim Speichern geprüft, aber **nie abgerufen** (kein SSRF), HTML geht erneut durch `ammonia`, Titel, Auszug und Schlagwörter werden gekürzt und normalisiert, ungültige Einträge werden gezählt (`invalid`). Duplikate (`user_id`, `url`) bleiben unverändert. Limits: 64 MiB, 20.000 Artikel, 4 MiB je Artikel, ein Import gleichzeitig, Ratenbegrenzung pro Benutzer (`export_user` 5, danach 1/min; `import_user` 3, danach 1 alle 10 min). Export lehnt `Sec-Fetch-Site: cross-site` ab. Neue Abhängigkeit `futures-util` (nur `stream::unfold` für den Export-Stream, ohne Standard-Features).
- **Markierungen und Notizen** (`highlights.rs`, `frontend/public/js/highlights.js`, Migration 0005 `highlights`): Im Lesemodus wählt der Benutzer Text aus, ein Bedienfeld am unteren Rand bietet 5 vorgegebene Farben (`PRESET_COLORS`) und eine eigene Farbe (`input type=color`, die zuletzt gewählte merkt sich `localStorage` als Bequemlichkeit). Die Farbe ist beliebiges `#rrggbb`, das Backend prüft die Form und speichert Kleinbuchstaben. Die Notiz ist optional (Klartext, max. 2000 Zeichen, nur über `textContent` angezeigt), sie wird nach dem Markieren im Bedienfeld oder durch Klick auf die Markierung oder die Notizkarte angelegt, geändert und gelöscht. API: `GET/POST /api/articles/{id}/highlights`, `PATCH/DELETE /api/highlights/{id}` (`note: null` löscht die Notiz); jede Abfrage filtert nach `user_id`, fremde Daten sind 404; höchstens 500 je Artikel (409). **Verankerung:** Position (`start`/`end` in UTF-16-Einheiten über alle Textknoten des dargestellten Artikels) plus Wortlaut mit je 32 Zeichen Umgebung (`quote`, `prefix`, `suffix`, W3C-„Text Quote“-Idee). Passt die Position nicht zum Wortlaut, wird die Stelle über den Wortlaut gesucht; sonst steht die Notiz mit dem Hinweis „Textstelle nicht mehr gefunden“ am Rand. Dargestellt als `<mark class="hl">` (Farbe als CSS-Variable `--hl` per CSSOM, wegen der CSP kein `style`-Attribut im HTML). Notizen stehen ab 72 rem Breite im rechten Rand auf Höhe der Markierung (Überschneidungen werden nach unten verschoben), schmaler unter dem Text. „Markierungen ausblenden“ blendet Farben und Notizen aus (auch das Anlegen ist dann aus), die Wahl merkt sich `localStorage`. Export und Import: Dateiversion 2 mit `highlights` je Artikel (ohne Ids, `start`, `end`, `quote`, `prefix`, `suffix`, `color`, `note`, `created_at`); Version 1 lässt sich weiter importieren. Jede Markierung wird beim Import einzeln mit denselben Regeln wie die API geprüft (ungültige werden gezählt: `highlights_invalid`), höchstens 500 je Artikel. Bei Artikeln, die es schon gibt, bleibt alles unverändert, also kommen auch keine Markierungen dazu.
- **PWA und Offline-Lesen** (`frontend/public/sw.js`, `manifest.webmanifest`, `js/offline.js`): Die App ist installierbar (Manifest, Icons in `icons/`, `display: standalone`) und lässt sich ohne Internet starten und lesen. **Voraussetzung ist HTTPS** (oder localhost): Ohne HTTPS (z. B. direkter Zugriff auf Port 3000 ohne Proxy) registriert der Browser den Service Worker nicht, dann gibt es weder Installation noch Start ohne Netz; die App läuft wie bisher. **Service Worker:** hält nur die App-Dateien (Liste `SHELL` in `sw.js`, ein Test prüft die Vollständigkeit gegen `js/`), Strategie „Netz zuerst mit 4 s Zeitlimit, sonst Cache“ (keine Versionsnummer zu pflegen, HTML und Skripte bleiben konsistent). Er fasst `/api/*`, fremde Adressen und alle Nicht-GET-Anfragen **nie** an, Antworten der Schnittstelle landen nie im Cache des Workers. **Einzige Ausnahme:** die Artikelbilder (`/api/articles/{id}/images/{id}`, nur GET, siehe „Lokale Bilder“): Der Worker liest für sie den Cache `leseliste-images` (Cache zuerst, sonst Netz) und schreibt nie hinein. Das Backend liefert alle Frontend-Dateien mit `Cache-Control: no-cache` und ETag aus (304 bei Gleichstand), damit `sw.js` nie veraltet. **Artikel-Speicher** (IndexedDB `leseliste-offline`, nicht im Service Worker): die 30 neuesten ungelesenen Artikel (Abgleich über `GET /api/articles?read=false`, dann je Artikel `GET /api/articles/{id}`, das jetzt auch `highlights` liefert) plus jeder geöffnete Artikel (14 Tage, höchstens 30). Gespeichert wird, was die Schnittstelle liefert (bereits bereinigt, Anzeige weiter nur über `safe-html.js`). Einstellung pro Gerät unter `#/account/offline` (`localStorage`, Standard an). **Datenschutz:** Besitzer wird gemerkt (`adopt`); alles wird beim Abmelden, bei 401 (Sitzung abgelaufen) und beim Kontolöschen gelöscht, ein anderer Benutzer verwirft die Daten des vorigen. Abmelden ohne Verbindung wird abgelehnt (die Sitzung soll wirklich enden). **Verhalten:** Lesemodus zeigt die gespeicherte Fassung sofort und gleicht danach mit dem Server ab; die Liste zeigt bei Fehler sofort, bei hängender Verbindung nach 2,5 s die gespeicherten Artikel (Filter, Schlagwörter und Suche laufen dann lokal, Akzente und Groß-/Kleinschreibung egal) mit Hinweis „Keine oder schlechte Verbindung“. Beim Start wartet die App höchstens 3 s auf `/api/me`. Offline lässt sich nur der Gelesen-Status ändern (vorgemerkt in IndexedDB, wird beim Abgleich gesendet, letzte Änderung gewinnt); Schlagwörter, Markierungen, Notizen, Speichern und Löschen brauchen eine Verbindung. Anfragen haben ein Zeitlimit (20 s, Artikel speichern 60 s, Import 5 min), danach gilt der Server als nicht erreichbar (ApiError Status 0). **Teilen:** `share_target` (GET auf `/`) speichert die erste http(s)-Adresse aus `url`, `text` oder `title` nach der Anmeldung über `POST /api/articles` (unter Android im Teilen-Menü der installierten App; iOS kennt das nicht, dort bleibt der Kurzbefehl). Neue Testabhängigkeit `fake-indexeddb` (nur `frontend/tests`, IndexedDB gibt es in jsdom nicht).
- **Ein Binary** (`static_files.rs`, Crate `rust-embed` 8 plus `mime_guess` für die Content-Types; Hash für den ETag liefert rust-embed selbst): `frontend/public` wird beim Kompilieren ins Binary eingebettet (Release), im Debug-Build von der Platte gelesen (`rust-embed/debug-embed` erzwingt das Einbetten). Der Router hat `/api` und als `fallback` die Dateien (nur GET/HEAD, `/api/...` liefert nie HTML, unbekannte Pfade 404; kein SPA-Fallback, das Routing läuft über `#/`). Die Sicherheits-Header (nosniff, X-Frame-Options, Referrer-Policy, CSP) setzt eine Middleware auf alle Antworten, früher die Caddyfile. Komprimierung übernimmt der vorgeschaltete Caddy (`encode`). **Betrieb:** ein Image `ghcr.io/<repo>`, Build-Kontext ist das Repository-Wurzelverzeichnis; die Compose-Datei veröffentlicht keinen Port, der Container hängt im Docker-Netz des vorhandenen Caddy (`PROXY_NETWORK`), und Caddy braucht nur `reverse_proxy app:3000`. Die Variante mit zwei Containern (eigenes Caddy-Image, Dev-Compose) wurde entfernt; lokal genügt `cargo run` auf :3000 (Ratenbegrenzung dort per `RATE_LIMIT_ENABLED=false` abschaltbar). Das Backend darf nie ohne Proxy aus dem Internet erreichbar sein. Neue Abhängigkeiten `rust-embed` (Einbetten samt Platten-Modus im Debug, ohne eigenen Build-Schritt) und `mime_guess`.
- **Leseeinstellungen** (`frontend/public/js/reading.js`, Styles in `style.css`, kein Backend): Schriftart (Systemschrift, Serif, Verdana-artig breit, Monospace; nur lokale Schriften, keine Webfonts), Textgröße (80–200 %), Textbreite (40–100 Zeichen pro Zeile, per `ch`), Zeilenabstand (1,3–2,2), Textausrichtung (Linksbündig, Blocksatz: nur Fließtext `p`, `li`, `blockquote`, `figcaption` mit `hyphens: auto`, die Trennung folgt dem `lang` des Artikels (siehe „Extraktion“), ohne Angabe dem deutschen der App), Farbschema (Gerät, Hell, Dunkel) und Kontrast (Weich, Normal, Hoch, wirkt in Hell und Dunkel). Gespeichert **pro Gerät** in `localStorage` (`leseliste-reading`, nur Bequemlichkeit, die Voreinstellung wird nicht gespeichert; `normalize` begrenzt alle Werte und verwirft Kaputtes, auch bei `storage`-Ereignissen anderer Tabs). Angewendet über `data-theme`, `data-contrast`, `data-reading-font`, `data-reading-align` am `<html>` und CSS-Variablen (`--reading-size`, `--reading-leading`, `--reading-measure`) per CSSOM, wegen der CSP kein `style`-Attribut. Farben nutzen `light-dark()` und `color-scheme` (Chrome 123, Safari 17.5, Firefox 120 oder neuer): ein Satz Variablen je Kontraststufe statt doppelter Dark-Mode-Blöcke; Hell/Dunkel erzwingen heißt nur `color-scheme` setzen. `meta theme-color` folgt dem erzwungenen Schema. Die Lesespalte `.reading-scope` trägt Schrift, Größe, Zeilenabstand und Breite (Bedienelemente darin behalten die Oberflächenschrift); `#app` ist bei Lesemodus und Darstellungsseite unbegrenzt breit. Bedienung: Knopf „Aa“ im Lesemodus (Bedienfeld, Escape schließt) und Seite `#/account/display` (Menü „Darstellung“, mit Vorschau); beide nutzen `mountControls` und bleiben über das Ereignis `leseliste:display` synchron. Randnotizen der Markierungen stehen nur dann im rechten Rand, wenn dort mindestens 16 rem frei sind (`hasRoomForMargin` in `highlights.js`), und werden bei jeder Änderung neu angeordnet. Der Service Worker kennt `reading.js` über `SHELL`, die Einstellungen funktionieren offline.
- **Leseposition** (`frontend/public/js/position.js`, Migration 0007 `articles.read_pos`): Das Frontend merkt sich still (keine Bedienung, keine Anzeige, Fehler bleiben unbemerkt), wo der Benutzer im Artikel steht, und springt beim Öffnen dorthin zurück. **Darstellung der Position:** Textoffset in UTF-16-Einheiten über den dargestellten Artikeltext (`collectText` aus `highlights.js`, dieselbe Zählung wie bei den Markierungen), keine Pixel: damit stimmt sie bei anderer Schrift, Breite oder Gerät. Gemessen wird über Blockelemente (`BLOCKS`, nächstes Blockelement über dem Textknoten) und anteilig darin, nicht über einzelne Zeichen; die Lesezeile liegt 24 px unter dem Fensterrand und gilt beim Speichern wie beim Wiederherstellen. **Regeln:** (1) Nur ungelesene Artikel merken eine Position; `is_read = true` setzt `read_pos` auf 0, das entscheidet das Backend in **einer** UPDATE-Anweisung mit dem danach geltenden Status (`PATCH /api/articles/{id}` mit `read_pos`, 0 bis 10.000.000, sonst 400), damit auch eine verspätete Positions-Anfrage nach „gelesen“ nichts zurückbringt. Gelesene Artikel starten oben. (2) Ist das Textende im Fenster zu sehen (`reachedEnd`, 4 px Toleranz), gilt der Artikel als zu Ende gelesen und die Position wird 0, ohne ihn als gelesen zu markieren. Wer danach wieder hochscrollt, hat wieder eine aktuelle Stelle (die Position ist immer das, wo man beim Verlassen steht; das Textende nur kurz anzusehen, um die Länge zu prüfen, kostet die Stelle also nichts). (3) Nur wenn der Benutzer gescrollt hat (`dirty`), wird gespeichert, nie allein durch das Öffnen. **Speichern:** höchstens einmal pro Sekunde während des Scrollens, sofort beim Verlassen der Ansicht (`show()` ruft `position.end()` vor dem Ausblenden, denn danach lässt sich nichts mehr messen), bei `visibilitychange` (hidden) und `pagehide` (mit `keepalive`). Eine Verschiebung unter 30 Zeichen wird nicht gespeichert (Ausnahme: nach 0). Scroll-Ereignisse der Wiederherstellung (400 ms Ruhe) zählen nicht. **Wiederherstellen:** aus der Kopie auf dem Gerät sofort, dann die Position des Servers, solange der Benutzer noch nichts getan hat (`wheel`, `touchstart`, `keydown`, `pointerdown`, `mousedown`): so gewinnt eine auf einem anderen Gerät weitergelesene Stelle. Laden Bilder nach und verschieben den Text, wird die Stelle nachgeführt (`load` im Capture-Modus, ebenfalls nur ohne Eingabe). **Offline:** die Position steht sofort in der Kopie (`offline.setPosition`) und wird bei Unerreichbarkeit zusammen mit dem Gelesen-Status in derselben Warteschlange vorgemerkt (`offline.queueChange`, je Artikel zählt die letzte Änderung, `is_read: true` erzwingt auch dort `read_pos: 0`); eine direkt gesendete Position entfernt eine ältere Vormerkung (`dropQueuedPosition`), sonst würde der Abgleich sie überschreiben. **Nicht enthalten:** Die Position steht weder in der Artikelliste noch im Export (flüchtiger Zustand, Dateiversion bleibt 2). Neue Abhängigkeiten gibt es keine. **Bekannte Grenze:** In echten Browsern gemessen wird mit `getBoundingClientRect`; die Frontend-Tests arbeiten wegen jsdom mit einem simulierten Layout (`tests/leseposition.test.mjs`), prüfen also die Logik, nicht das Verhalten der Browser-Layoutengine.
- **Zur-Liste-Link im Lesemodus** (`frontend/public/js/backlink.js`, `.back-bubble` in `style.css`, kein Backend): Der Link „← Zur Liste“ steht oben normal im Text (`#reader-back`). Ist er nach oben aus dem Bild gescrollt, erscheint zusätzlich eine schwebende Bubble (`#reader-back-float`, `position: fixed`, oben links, Safe-Area-Abstände, z-index 15 zwischen Menü 10 und Markierungsfeld 20). Am Textende steht ein zweiter normaler Link (`#reader-back-bottom`); ist der im Bild, verschwindet die Bubble (`floatVisible`: oben weg und unten noch nicht zu sehen). Gemessen wird per `getBoundingClientRect` bei `scroll`, `resize` und nachladenden Bildern (höchstens einmal pro Bild per `requestAnimationFrame`), bewusst nicht per IntersectionObserver: der kennt den Zustand beim erneuten Öffnen oder nach einem Sprung der Leseposition nicht neu. `show()` ruft `backBubble.reset()`, damit die Bubble beim Ansichtswechsel nicht an der alten Stelle aufblitzt. `prefers-reduced-motion` schaltet die Animation ab. Der Service Worker kennt `backlink.js` über `SHELL`. **Bekannte Grenze:** Die Tests (`zurueck.test.mjs`) arbeiten mit simuliertem Layout, prüfen also die Logik, nicht die Layoutengine echter Browser.
- **Lokale Bilder** (`images.rs`, `imageproc.rs`, Migration 0008 `article_images`, `safe-html.js`): Hotlink-Schutz fremder Server, Link-Fäule, Tracking und Offline-Lesen sprechen dafür, die Bilder der Artikel selbst vorzuhalten. **Ablauf:** `articles::save_article` trägt jedes `<img src>` des bereinigten HTML (`extract::image_urls`, absolut gegen die Artikel-URL, nur http(s), höchstens 30 je Artikel) als Zeile in `article_images` ein (`pending`) und weckt den Worker (`tokio::sync::Notify`); die Antwort wartet nicht auf die Bilder. Der Worker (`images::run_worker`, in `main` gestartet, kein Cronjob, kein zweiter Dienst) holt je Bild mit dem SSRF-geschützten `Fetcher::fetch_image` (Referer = Artikel-URL ohne Fragment, damit Hotlink-Sperren durchlassen; Limit `IMAGE_MAX_BYTES`), verkleinert in `spawn_blocking` und speichert das Ergebnis als BLOB (`done`). Höchstens `IMAGE_CONCURRENCY` Bilder gleichzeitig. Die Warteschlange liegt in der Datenbank: `recover` macht beim Start unterbrochene Aufträge (`working`) wieder zu `pending`, ein Minutentakt holt fällige Wiederholungen. Wiederholt wird nur bei vorübergehenden Fehlern (Zeitüberschreitung, Verbindungsfehler, 5xx, 429), dreimal mit 60 s und 300 s Abstand, alles andere ist endgültig `failed`. Gescheiterte Bilder bleiben Original-Links. **Verkleinern** (`image` 0.25 ohne Standard-Features, nur JPEG/PNG/GIF/WebP, rein in Rust, passt zum statischen musl-Build): Format wird an den Bytes erkannt, nie am Content-Type (kein SVG, kein AVIF); Maße werden aus dem Kopf **vor** dem Dekodieren geprüft (höchstens 40 Megapixel, zusätzlich `Limits::max_alloc`, gegen Bildbomben); längste Seite höchstens 1600 px (Lanczos3). JPEG wird immer neu kodiert (Qualität 82), PNG bleibt PNG (große PNG ohne Transparenz werden JPEG, wenn das mindestens 40 % spart), WebP nur bei mehr als 1600 px neu kodiert (die Bibliothek schreibt WebP nur verlustfrei), GIF bleibt unverändert (Animation), Bilder unter 8 px gelten als Zählpixel und werden verworfen, höchstens 5 MiB gespeichert. Beim Neukodieren fällt EXIF (Aufnahmeort) weg, die Drehung wird vorher angewendet. Das Original wird nie gespeichert; die Verkleinerung ist bewusst endgültig („zum Lesen“). **Speicher:** BLOB in SQLite (Löschen per `ON DELETE CASCADE`, Sicherung und Benutzertrennung wie bei allen Daten). Erwartung: etwa 0,2–0,5 MB je Artikel, bei tausend Artikeln einige hundert MB. **Anzeige:** Das gespeicherte HTML behält die Original-Adressen (Export und Import bleiben unverändert). `GET /api/articles/{id}` liefert `images` (`{Original-URL: {src, width, height}}`, nur fertige Bilder); `safe-html.js` tauscht beim Aufbau die Adresse gegen `/api/articles/{id}/images/{image_id}` (nur dieses Muster wird akzeptiert), setzt `width`/`height` (kein Springen des Textes) und merkt die Original-Adresse in `data-origin`; `applyLocalImages` tauscht Bilder nachträglich, ohne den Text neu aufzubauen (die Leseposition bleibt). Die Auslieferung prüft Benutzer und Artikel (fremde Daten sind 404), setzt den Content-Type aus der eigenen Verarbeitung und `Cache-Control: private, max-age=31536000, immutable` (der Inhalt einer Bild-Id ändert sich nie, Nachladen betrifft nur nicht fertige Bilder). Die CSP bleibt unverändert (`img-src 'self' https: data:`), weil gescheiterte Bilder weiter vom Original kommen. **Nachladen:** `POST /api/articles/{id}/refresh-images` reiht Bilder älterer und importierter Artikel ein und versucht endgültig gescheiterte erneut (zählt wie ein Abruf für `fetch_user`); im Lesemodus erscheint „Bilder nachladen“ nur, solange noch Bilder von der Originaladresse kommen. **Import** reiht nie etwas ein (Dateiinhalt wird nie abgerufen), der Export enthält keine Bilddaten. **Offline:** Die Zuordnung steht im Offline-Speicher, die Bilddateien liegen im Cache-Speicher des Browsers (Cache API, Name `leseliste-images`), ausdrücklich nicht im HTTP-Cache, den der Browser nach Belieben räumt. Geschrieben wird nur von `offline.js` (`cacheImages`, nur wenn „Offline-Lesen“ an ist): nach dem Öffnen eines Artikels und im Abgleich (`syncImages` holt Fehlendes und entfernt alles, was zu keinem gespeicherten Artikel mehr gehört). Der Service Worker liest diesen Cache für genau das Adressmuster, schreibt nie und räumt ihn beim Aktivieren nicht ab. Damit der Abgleich Artikel neu lädt, wenn Bilder erst nach dem Speichern fertig wurden, nennt jede Artikelzusammenfassung `image_count` (fertige Bilder); weicht er von der Kopie ab, wird der Artikel neu geholt. Gelöscht wird der Cache überall dort, wo auch der Offline-Speicher gelöscht wird (`clearAll`: Abmelden, 401, Kontolöschen, anderer Benutzer, Offline-Lesen aus, „Gespeicherte Artikel löschen“); `remove(id)` nimmt die Bilder des Artikels mit. Ohne Verbindung, bei vollem Speicher oder ohne Cache API endet das Vorladen still. Umfang: höchstens 30 + 30 Artikel, grob 10 bis 30 MB; `navigator.storage.persist()` wird bereits beim Einschalten angefragt. Neue Abhängigkeit `image` (Begründung: Verkleinern ohne C-Bibliotheken); im Debug-Build sind `image` und seine Codecs optimiert (`[profile.dev.package.*]`), sonst dauern die Tests ein Mehrfaches. **Bekannte Grenzen:** Bot-Schutz oder Login-Pflicht auf dem Bild-Server, Lazy-Loading-Platzhalter (`data-src`) und `srcset` hängen davon ab, was Readability übrig lässt; solche Bilder bleiben Original-Links. `IMAGE_STORE_ENABLED=false` schaltet alles ab.
- **Lesefilter merken** (`app.js`, `loadReadFilter`/`saveReadFilter`, kein Backend): Die Auswahl Alle/Ungelesen/Gelesen steht pro Gerät in `localStorage` (`leseliste-read-filter`, nur `true` oder `false`, „Alle“ löscht den Eintrag, Fehler beim Speicher werden ignoriert, ungültige Werte gelten als „Alle“). Sie gilt beim Start und nach Abmelden/Anmelden weiter (Oberflächeneinstellung, kein Nutzerdatum). Nach dem Speichern eines Artikels werden nur Suchtext und Schlagwort zurückgesetzt, die Auswahl bleibt; ist „Gelesen“ gewählt, erscheint ein Hinweis, dass der neue (ungelesene) Artikel dort nicht steht.
- **Passkeys** (`passkeys.rs`, `cli.rs`, `js/passkeys.js`, Migration 0009 `passkeys`): Zusätzliche Anmeldung neben dem Passwort, mehrere je Benutzer (max. 10), Verwaltung unter `#/account/passkeys`, Anmeldung ohne E-Mail („Mit Passkey anmelden“, discoverable credentials). **Regeln:** (1) Das Passwort bleibt Pflicht und Rückfallweg, es gibt keine Konten nur mit Passkey. (2) Einrichten und Löschen verlangen das Passwort (`auth::confirm_password`, Ratenbegrenzung `password_user`), damit eine gekaperte Sitzung keine Passkeys anlegen kann. (3) Der Server setzt `residentKey: required` selbst (`require_resident_key`), `user_handle` ist je Benutzer eine zufällige UUID. (4) RP-ID und Origin kommen **nur** aus der Konfiguration (`PASSKEY_ORIGIN`, https außer localhost, kein Pfad), nie aus der Anfrage; ohne Angabe sind Passkeys aus (`GET /api/features`). Die RP-ID lässt sich später nicht ändern, alle Passkeys wären dann wertlos (das Passwort geht weiter). (5) Zustand der Challenges nur im Speicher (Mutex, 6 min Gültigkeit, einmalig verwendbar, Obergrenzen); ein Neustart bricht nur laufende Vorgänge ab. Die Startpunkte für die Anmeldung liegen hinter dem IP-Limit `auth`. (6) Der Zähler wird nach jeder Anmeldung gespeichert (`update_credential`), Passkeys liegen als JSON in SQLite (kein geheimes Material). **Bibliothek:** `webauthn-rs` 0.6.1-dev mit Feature `conditional-ui`, weil sie rein in Rust (RustCrypto) läuft; die stabile 0.5 braucht OpenSSL und würde den statischen musl-Build des Images brechen. Der Versionsstand ist eine Vorabversion: bei Updates die Tests in `tests/passkeys.rs` prüfen. Weitere Abhängigkeiten: `rpassword` (Passwortabfrage im Betreiber-Befehl ohne Echo), nur für Tests `p256`, `ciborium`, `base64` (Test-Authenticator `tests/common/authenticator.rs`; `webauthn-authenticator-rs` taugt dafür nicht, es kennt keine discoverable credentials). **Frontend:** Umwandlung base64url ↔ ArrayBuffer von Hand, ohne `parseCreationOptionsFromJSON` und `toJSON` (fehlen in älteren Safari-/Chrome-Versionen); die Frontend-Tests nutzen eine Mock-Schnittstelle (`tests/soft-authenticator.mjs`) gegen das echte Backend. **Betreiber-Reset:** `readlater-backend reset-credentials` setzt in einer Transaktion ein neues Passwort, beendet alle Sitzungen und entfernt auf Wunsch Passkeys und Teilen-Tokens. Er nutzt `db::connect` (WAL, `busy_timeout`) und läuft deshalb bei laufendem Server. Einen Reset per E-Mail gibt es bewusst nicht (kein Mailversand, keine Angriffsfläche). Das Teilen per Token (`/api/share`) ist von Passkeys unabhängig.
- **Registrierung**: per `REGISTRATION_ENABLED=false` abschaltbar.
- **Artikel abrufen (SSRF-Schutz)**: nur http/https ohne Zugangsdaten; ein eigener DNS-Resolver (`PublicOnlyResolver` in `fetch.rs`) liefert nur öffentliche IPs, das gilt damit auch für Redirects (max. 5, jeder Hop wird geprüft) und gegen DNS-Rebinding. Kein Proxy, Gesamt-Timeout, Größenlimit auf die entpackten Bytes (Gzip-Bomben), nur HTML, gleichzeitige Abrufe begrenzt (sonst 429). Duplikate (pro Benutzer, ohne Fragment) liefern 409 ohne erneuten Abruf.
- **Extraktion**: `dom_smoothie` (Readability), Ergebnis wird mit `ammonia` bereinigt. `content` = bereinigtes HTML, `content_text` = Klartext (für FTS5 in Schritt 3), `excerpt` (Migration 0002). TLS über rustls mit `ring` (einfacher für musl-Builds als aws-lc-rs). **Tiefenlimit:** `extract::exceeds_max_depth` lehnt vor dem Parsen HTML mit mehr als 256 Ebenen ab (`TooComplex`, beim Import ungültig). Grund (gemessen): Readability und `ammonia` werden bei tausenden geschachtelten Elementen quadratisch teuer (5.000 Ebenen > 2 Minuten CPU in einem Blocking-Thread), schon der Parser ist nicht linear, daher keine Prüfung am geparsten Baum. Die Prüfung ist ein linearer Durchgang über die Tags (offene minus geschlossene Elemente; Kommentare, Skripte/Styles und Elemente mit optionalem Ende-Tag wie `p`, `li`, `td` zählen nicht), bewusst grob: nicht geschlossene Tags zählen als offen. Ohne neue Abhängigkeit. **Sprache des Artikels** (Migration 0006, `articles.lang`, ISO 639-1, `NULL` = unbekannt): `extract::detect_language` erkennt sie mit `whatlang` (Trigramme, rein in Rust, ohne Modelldateien, kleine Abhängigkeit) aus `content_text`, höchstens die ersten 4.000 Zeichen. Das `lang`-Attribut der Seite wird bewusst **nicht** gelesen (unzuverlässig, oft falsch oder fehlend). Nur sichere Ergebnisse (`is_reliable`) und Sprachen mit zweistelligem Code zählen, sonst `NULL`: lieber keine Angabe als eine falsche. Die Erkennung läuft nur beim Speichern und beim Import (dort aus dem Text, ein `lang` aus der Datei zählt nicht, die Datei gilt als feindlich), nicht beim Start und nicht als Hintergrundjob; ältere Artikel bleiben `NULL`. Das Feld steht in `GET /api/articles/{id}` (nicht in der Liste und nicht im Export), der Lesemodus setzt es als `lang` an Titel und Text (`setArticleLang` in `app.js`), der Offline-Speicher behält es. Ohne Wert gilt `lang="de"` der App.
- **Frontend-Regel**: Ausnahme ist `js/safe-html.js`: Artikel-HTML wird per DOMParser geparst und mit createElement über eine Positivliste neu aufgebaut (zusätzlich zu ammonia). Die CSP erlaubt `img-src 'self' https: data:`.
- **Frontend-Regel**: nie `innerHTML` mit Daten aus der API. Immer `textContent` oder DOM-Methoden. Die CSP (`static_files.rs`) erlaubt keine Inline-Skripte.
- **Build-Zeit**: Im Release-Profil ist LTO aus. Gemessen (2 Kerne, lokal): Neubau nur des eigenen Codes 68 s mit `lto = "thin"` gegen 18 s ohne, volle Kette 216 s gegen 175 s, Binary in beiden Fällen etwa 13 MB. Der Docker-Build cached die Abhängigkeiten in einer eigenen Schicht (nur `Cargo.toml` und `Cargo.lock`); ändert sich eine der beiden Dateien, werden alle Abhängigkeiten neu gebaut.
- **Versionen** (Stand Okt. 2026): sqlx 0.9 akzeptiert nur `&'static str` als SQL (dynamische Strings nur mit `AssertSqlSafe`), argon2 0.6 nutzt `password_hash::phc::PasswordHash` und erzeugt den Salt selbst.
